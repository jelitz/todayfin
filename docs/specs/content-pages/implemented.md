# Implemented — content-pages

## 설계 결정

- **`parseHash`를 `lib/route.ts`로 분리**: 라우트가 2개에서 4개로 늘면서 단위 테스트 가치가 생겼다. `App.tsx` 안의 로컬 함수는 테스트가 불가능했다.
- **GNB 탭을 `<button>`이 아니라 `<a href>`로**: 진짜 페이지 내비게이션이므로 앵커가 의미상 맞고, 새 탭으로 열기·링크 복사 같은 브라우저 표준 동작을 공짜로 얻는다. 홈 카드가 `role="button"`인 것과 대비되는데, 카드는 모달을 여는 동작이라 성격이 다르다.
- **`useActiveSection` 삭제**: GNB 활성 탭 판정이 유일한 호출처였다. 홈 화면에서 섹션으로 점프하는 수단이 없어졌지만, 지표가 12개뿐이라 스크롤 부담이 크지 않다고 판단해 대체 UI를 만들지 않았다(YAGNI).
- **소개 페이지가 `SECTIONS`를 재사용하지 않음**: 소개 문구의 분류·순서는 대시보드 레이아웃과 독립적으로 바뀔 수 있다(예: 소개에서는 국채 3종을 한 항목으로 묶어 설명). id 기반 상수와 사람이 읽는 설명문은 결합도가 다르다.
- **미디어 파이프라인을 `collect.py`와 분리**: 도메인이 다르고(주가 시계열 vs 미디어 목록), 실패 정책도 다르다. 주가는 3영업일 stale을 워크플로우 실패로 승격시키지만, 영상이 며칠 안 올라오는 것은 정상이다.
- **`youtube_api.fetch`의 시그니처가 기존 어댑터와 다름**: 기존은 `fetch(indicator_id, start, end) -> DataFrame`이지만 미디어는 시계열이 아니라 목록이라 pandas가 불필요하다. `sources/`에 두는 것은 "외부 데이터 어댑터"라는 역할이 같기 때문.
- **새 영상이 없으면 빌드·배포 스킵**: 매시간 실행이라 무변경 시에도 배포하면 하루 24번 불필요한 Pages 배포가 발생한다. `git diff --cached --quiet` 결과를 스텝 output으로 넘겨 조건부 실행한다.
- **게시일로 `contentDetails.videoPublishedAt` 사용**: `snippet.publishedAt`은 업로드 플레이리스트에 추가된 시각이라 비공개→공개 전환 등에서 실제 공개 시각과 어긋날 수 있다.

## 계획과의 편차: RSS → YouTube Data API v3 전환

`tasks.md` Task 4·5는 유튜브 RSS 피드(`youtube.com/feeds/videos.xml`)를 쓰도록 계획했고 로컬에서는 정상 동작했지만, **GitHub Actions 러너에서는 쓸 수 없었다.**

**증상**: 첫 CI 실행(run `30791245666`)에서 RSS가 404. 로컬(한국 가정용 IP)에서는 같은 URL이 200.

**진단 과정과 두 번의 실패**:

1. **UA 누락 가설** — `requests` 기본 UA(`python-requests/x.y`)가 차단된다고 보고 브라우저 UA를 추가했다. 그런데 UA를 추가한 뒤 로컬에서도 404가 나기 시작해 가설이 흔들렸다. UA 유무를 3회 교차 샘플링한 결과 **동일 시점에는 UA와 무관하게 같은 코드**(404, 200, 404)가 나왔다 — UA는 무관했고, 처음의 "UA가 해결했다"는 판단은 타이밍이 겹친 착시였다.
2. **스로틀링 가설** — 짧은 간격 반복 호출로 인한 일시적 차단으로 보고 재시도를 2회(5·15초)에서 4회(10·30·60·90초)로 늘렸다. 재실행(run `30791734425`) 결과 06:55:00 시작 → 06:58:11 실패, 즉 **3분에 걸친 5회 시도가 전부 404**. 재시도로는 해결되지 않는 IP 기반 차단으로 확정.

같은 문제에 두 번 실패한 시점에서 접근을 바꿨다. 이 프로젝트가 Stage 1에서 Stooq에 겪은 것과 같은 유형(데이터센터 IP 차단)이다.

**해결**: YouTube Data API v3로 전환(`pipeline/sources/youtube_api.py`). 공식 API라 데이터센터 IP에서도 정상 동작한다. 실행당 2유닛(`channels.list` 1 + `playlistItems.list` 1)이라 매시간 호출해도 하루 48유닛으로, 무료 한도 10,000유닛/일에 여유가 크다. `YOUTUBE_API_KEY` secret이 필요해 사용자 액션이 추가됐다(ECOS·KRX와 동일한 패턴).

**검증**: 키 등록 후 run `30805781019`에서 `[ok] 영상 15건 저장` 확인, 커밋·배포까지 성공.

RSS 구현·테스트·픽스처와 `defusedxml` 의존성은 사용처가 없어져 삭제했다(필요 시 커밋 `917f886`에서 복원 가능).

**교훈**: 외부 소스는 로컬에서 되더라도 CI 환경(해외 데이터센터 IP)에서 별도 검증이 필요하다. 이 프로젝트의 Stage 1 스파이크 방법론이 정확히 이 문제를 잡기 위한 것이었는데, 이번엔 RSS가 "인증 불필요"라 안전하다고 보고 스파이크를 건너뛴 것이 원인이다.

## 검증 중 발견한 오진

브라우저 검증에서 알상무 카드의 썸네일이 전부 비어 보였다. DOM·네트워크를 확인한 결과 이미지는 15개 모두 정상 로드됐고(`naturalWidth: 480`, `complete: true`), CSS도 정상이었다(`392×220`, `opacity: 1`, `visibility: visible`). **스크린샷 캡처 시점에 lazy 이미지가 아직 페인트되지 않았던 것**으로, 코드 문제가 아니었다. 재캡처 시 정상 표시 확인.

## 범위에서 제외한 것과 이유

- **인스타그램(`alex.ods5`)**: Meta Business Discovery API는 (1) 대상 계정이 Business/Creator 계정이어야 하고 (2) 요청하는 앱이 App Review와 Business Verification을 통과해야 한다. 개인 프로젝트 규모에서 통과 가능성·소요 기간이 모두 불확실해 2단계 백로그로 이관했다.
- **유튜브 커뮤니티 게시글**: 공식 API에 해당 엔드포인트가 없고 RSS에도 포함되지 않는다. 비공식 HTML 스크래핑은 구조 변경·차단 리스크가 커서 사용자와 협의해 제외했다.
